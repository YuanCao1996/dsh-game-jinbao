# 自动播报延迟优化计划

## 一、先纠正一个判断（实测）

此前我把"播报晚到几分钟"归因于模型慢。实测 `agent-activity.jsonl` 里近 40 个回合：

```
中位数 4.5 秒   均值 5.7 秒   P90 7.6 秒   最大 36.6 秒
<10 秒 36 个 | 10-30 秒 3 个 | 30-60 秒 1 个
```

**模型不是瓶颈。** 真正的延迟在"事件发生"到"请求发出"之间，以及请求被丢弃后等下一次触发。

## 二、目标（可验收）

| 指标 | 现状 | 目标 |
|---|---|---|
| 关键事件（敌方成装 / 海克斯确认）到播报可见 | 3~11 分钟 | P90 ≤ 8 秒 |
| 关键时刻请求被丢弃率 | 未知（无埋点） | ≤ 5% |
| 模型回合 P90 | 7.6 秒 | 保持 ≤ 10 秒 |

## 三、分阶段

### P0 全链路埋点（半天，必须先做）

现在无法回答"这 3 分钟花在哪"。在 auto-coach 里记录带时间戳的阶段事件到 `logs/coach-timeline.jsonl`：

- `event_seen`（事件入队）→ `plan_built` → `scheduler_submit` → `scheduler_take`（含 lane）→
  `ask_start` → `ask_end` → `publish` ；被丢弃时记录 `skip` + 原因（throttle / busy / coalesce / deadline）

验收：任取一条播报，能从日志读出它每一段的耗时。

### P1 去掉对关键时刻的全局节流（1 天）

`auto-coach` 有 `now()-(store.lastAt??-Infinity)<30000` 的全局 30 秒节流。
敌方成装、海克斯确认、团灭这类事件即使命中也要等满 30 秒。

改法：节流只对 `situation`/`opening` 这类"可等待"的事件生效；`postAugment / enemyChange / ace / death` 直接放行。

### P2 请求被占用时的抢占（2~3 天，风险最高）

单一在途请求是 3~11 分钟的主因之一：一个慢回合没结束，后续关键时刻只能被丢弃或排队。

改法：
1. 给请求分级（手动提问 > 关键事件 > 常规刷新）
2. 高优先级到达时取消在途的低优先级回合
3. **必须验证取消的清理**：服务端任务是否真的停下（历史上有僵尸任务占额度的先例）

验收：连续触发两次关键事件，第二次的 `ask_start` 与第一次 `ask_end` 的时间差 < 2 秒。

### P3 事件合并与去重（1 天）

同一波连续事件（三件装备同时成型、连杀）会产生多次请求。按"同类事件 5 秒窗口合并"处理，
合并后只发一次，但播报覆盖全部要点。

### P4 前端呈现兜底（已部分完成）

本地规则先出短句（已做：敌方关键成装、海克斯承接语已按你的要求撤掉承接语），
模型播报到达后覆盖。这条不追求速度，只保证"没有空白期"。

## 四、执行顺序与验证

1. P0 埋点 → 用真实对局数据确认时间都花在哪一段（1 天后给出实测结论）
2. 依据实测结果决定先做 P1 还是 P2（我预期是 P1 便宜且立刻见效）
3. 每阶段都跑一遍上述三项指标，不达标不算完成

## 五、不做什么

- 不为了快而减少事实校验（编造冷却、价格比慢更糟）
- 不用固定模板冒充模型分析（模板只做"第一反应"，不承担分析）
- 不在未验证取消清理的情况下上抢占（僵尸任务会持续消耗额度）

### P0 为什么不达标

三个缺口：

1. **没有 turn id**。按「同局同 stage」硬配对，30 条播报算出中位 **515 秒**——纯属假数据；
   改成单飞配对（running→首个收尾事件）才对上 **22.2 秒**。现在谁读这份日志都会读错。
2. **没有 `event_seen / plan_built / scheduler_submit / scheduler_take / ask_start / ask_end`**。
   能读出「模型回合总耗时」，读不出「事件发生 → 请求发出」那段，而计划第三节明确说延迟就在那段。
3. **没有报告脚本**，只能人工写一次性分析。

### P1 复核时查出的两个新缺口

原计划以为「把 30 秒节流只留给可等待事件」就完事。实际复核发现节流搬了家：

1. `automatic-pacing.mjs` 的准入层有 `intervalMs = 60000`（按 topic 计）。`main.mjs` 没传值，走默认 60 秒。
   而 `allowed = !active && (urgent || !busy())` —— **urgent 只豁免语音队列 busy，不豁免这个 60 秒间隔**
   （`openFor()` 对 urgent 一视同仁）。后果：一次团灭/死亡边沿若落在上一次播报后 60 秒内，
   会被 `auto_deferred` 推到下一次，而死亡窗口只有 45 秒。
2. `auto-coach` 的抢先判断用的是 `canRequest()`，它只反映 `allowed()`，**不反映 `openFor()`**。
   于是「死亡不受背压限制」这条前置放行在真正的准入点被否掉，调度器再聪明也来不及。
   这就是 `retry_backoff` 116 次与 `output_backpressure` 568 次里的一部分。

这类豁免没有测试保护（`automatic-pacing-urgent.test.mjs` 只测了 busy 与单飞），所以一直没被发现。

### P2 路线复核（2026-11-15）：后台并行走不通，抢占其实可测

原本设想「急事另起一个后台任务并行跑，谁先回来先用」。查了服务端实现，这条路被策略挡死：

- `tasks.py create()` 里 `if any(task["owner"] == owner for task in active): raise TaskError("user_task_busy", 409)`
  —— **一个账号同时只允许一个未终态任务**。所以客户端的单飞不是偷懒，是服务端规定。
- 全局 `ThreadPoolExecutor(max_workers=max_running)`，`max_running = 2`
  —— 整个服务同时只跑 2 个任务，第 3 个直接 429 `agent_capacity`。同一玩家并行 2 个会挤掉别人。
- 就算放开，同一 `(owner, session)` 并发也不安全：`create()` 快照 `history`，任务结束时 append 用户和助手消息，
  两个并发任务会各 append 一遍，历史重复错序。

但「取消」这条路是真的能做，而且已经写好了，只是没人用：

- 服务端 `cancel()` 只设置 `threading.Event`，`runner` 在每一步之间检查，命中就 `process.kill()`
  杀掉子进程并抛 `task_cancelled`；`_run` 收尾时再判一次，状态落成 `cancelled`。
- 客户端 `createCloudAgent.close({reason:'preempt'})` 已经会打 `/tasks/:id/cancel`，并轮询到终态（上限 45 秒）。
- 手动提问抢占自动回合走的就是这条链，已有测试覆盖（`priority-recovery.test.mjs`）。

**结论：P2 不需要新机制，需要把「手动提问抢占」这套接给关键自动事件**（死亡边沿、海克斯确认、团灭）。
风险从「未知」降为「可测」：取消后服务端子进程被 kill，可以再实测一次
「取消后 activity 里不再出现 model_start/model_end、额度不再增长」来收口。

### 埋点顺手暴露的真主因（优先级应重排）

`skip` 原因分布（2 小时 17 分）：

| 原因 | 次数 | 含义 |
|---|---|---|
| `stale_facts` | 934 | 对局日志静默超过 2 分钟，整局被判死 |
| `output_backpressure` | 568 | 语音队列背压，事件被吞 |
| `busy` | 424 | 单飞：上一个回合 15~37 秒没跑完 |

第三才是排队（424，P2 想解决的正是这一段）。这跟第四节“依据实测决定先做 P1 还是 P2”的约定一致——
现在该先修断流与背压，抢占排在第三。

## 七、容量结论与 P2 改道（2026-11-15）

### 更正：机器不是 1 GB，`max_running=2` 是拍脑袋的默认值

上一版这里写的「2 个并发是机器到顶」**是错的**，原因是我把 `free -g` 的四舍五入当成了总量。实测：

```
内存   total 1870 MB   used 664   available 1206 MB   swap 已用 372 MB
CPU    2 核   load average 0.00 / 0.00 / 0.00（完全空闲）
```

`max_running` 的默认值写死在 `TaskStore.__init__(..., max_running=2)`，线上没有任何地方覆盖它。
也就是说 2 这个数是**代码默认值**，不是压测出来的容量上限。

单个任务的内存构成（服务器实测）：

| 项 | RSS |
|---|---|
| 纯 node 进程（`--max-old-space-size=128`） | 46 MB |
| 加载 worker 的模块图（runtime/adapter/policy/events/…） | 72 MB |
| `@deepseek-ai/dsh-llm` 这一层 | 约 +5 MB |
| 跑起来（历史回放 + 24 KB 上下文 + 工具结果 + 输出流） | 90~130 MB |

**为什么两个任务就是 180–260 MB**：`runner.py` 是 `subprocess.Popen([node, "--max-old-space-size=128", worker])`
——**每个任务起一个新的 node 进程**，进程之间零共享，所以内存严格按并发数线性叠加。46 MB 空壳 ×2 只是起步。

按 130 MB/任务、给系统留 400 MB 算，这台机器能跑 **6 个左右**；CPU 是网络等待型负载，基本不是约束。
所以正确的顺序是：先把 `max_running` 提到 4~6 观察，而不是先换机器。

更进一步（收益更大、改动也更大）：改成**常驻 worker 池**——常驻 N 个 node 进程、任务排队派发，
内存从 72 MB×N 降到约 72 MB+N×30 MB，还省掉每次任务 0.3~0.8 秒的 node 启动。
`createRuntime()` 是普通 async 函数、没有单例限制，同进程多实例在技术上可行，但要给 worker 加任务循环协议。

### P2 改道：急事走「无状态单次调用」的快通道

现状：**所有**请求（连多杀点评都在内）都走 `/tasks`，因此共享两道闸——「一个账号同时一个任务」和「全局 2 个 worker」。点评甚至要靠排在教练回合之前才抢得到槽位。

但代码里其实已经有两条「不占 worker 池的一次性模型调用」先例：

- `agent_dsh/screens.py`：截图分析直接调模型（`enable_thinking: false, max_tokens: 1024`），没有 agent 循环。
- 网关的 `/speech`、`/knowledge`：同步路由，只走 entitlements + rateGate + 一次远程调用，不占 DSH worker。

所以急事不必抢占，另开一条快通道即可：

```
POST /desktop/agent/advice-quick
  鉴权与限流：沿用 identity + entitlements + rateGate（每用户每分钟 ≤6 次）
  输入：桌面已采好的紧凑事实包（cloudContext 现成，不检索）
  调用：一次模型请求，enable_thinking:false，max_tokens ≤ 200
  输出：一句话播报，走现有 publish + validity 路径
```

三个好处：

1. **不占 worker 池**：只有一个 Python 线程 + 一次 HTTP 出网，1 GB 机器扛几十个并发不成问题（gunicorn 现配 8  threads）。
2. **天然避开那两个坑**：无状态、不写会话历史，所以不冲突历史、不触发 `user_task_busy`、也不会有僵尸任务。
3. **快**：现有模型步实测中位 **3.76 秒**；关思考 + 小 max_tokens 按多杀点评的量级预期 **2~4 秒**，正好塞进死亡（45 秒）、团灭/塔（15~20 秒）的窗口。

分流规则：`death / augment 确认 / ace / turret` 走快通道；`situation / enemyChange / ultimate / 开局策略` 走深通道。
深通道晚到的结果继续按 validity 覆盖（已有机制），不需要额外协调。

### 分流比例（实测，决定这条通道值不值得做）

近 2 小时 6 局共 65 个回合，按 stage 分布：

```
situation     32 (49%)   ← 策略型，留深度池
coordination   9 (14%)   ← 反应型，可走快通道
postAugment    7 (11%)   ← 反应型
death          5 ( 8%)   ← 反应型
ultimate       4 ( 6%)   ← 策略型
enemyChange    4 ( 6%)   ← 策略型
ace            2 ( 3%)   ← 反应型
selection/loading 各 1
```

反应型合计 **23 次（35%）**，策略型 42 次（65%）。也就是说：

- **提速**：这 35% 的回合从「排队 + 22 秒」压到 2~4 秒；
- **扩容**：深度池只承担剩下的 65%，同机器容量约 ×1.55（5~8 人 → 8~12 人）；
- **省钱**：快调用输入 2~4k token、输出 ≤200，比深度回合（多次调用、几万 token）便宜一个数量级。

35% 是**下限**：这 65 个回合里大量急事本来就被 `stale_facts`(934) / `busy`(424) 吞掉了，
系统健康时反应型占比只会更高。

注意这两件事不能互相替代：快通道不解决「深度分析本身受 2C1G 限制」，扩机器也不解决「急事排在深度回合后面」。

### 为什么不用 subagent

DSH 的 subagent 跑在**同一个 worker 的同一个 agent 回合内**：不新增 worker 槽位、不绕过 `user_task_busy`，
还要多花内存（这机器最缺的就是内存）和多一跳延迟。它解决的是上下文隔离，不是并发，所以帮不上这个忙。

### 三档处置

1. **立刻可走快通道（0% 检索，只用本地事实）**：`death 38 + ace 32 + coordination 17 + enemyChange 13 + turret 2 + ultimate 2 + inhib 1` = **106 回合，27.5%**。
   这些回合现在毫无必要地等了 13~17 秒并占掉 worker 槽位；快通道把它们压到 2~5 秒（praise 实测 5.4 秒即此形态）。
2. **改造后可走快通道**：`postAugment 61`（16%）。它 87% 的时间花在检索海克斯效果文本上，而服务端 `tasks.py` 里已有
   `augment_effects()`，客户端也已经在 context 里带了 `owned_augments` 名字——把效果文本预取进事实包，这条就能脱离 agent。
   合计可分流 **167/385 = 43%**。
3. **必须留深度**：`equipment 168`（装备价格与克制资料，单体最大）、`situation 21`、`augment 4`、`selection 4`、`opening/loading`。
   这里面 `equipment` 一个就占 44% 的回合和最多检索次数，要降本得靠本地装备索引，不是靠快通道。

### 顺带修正一个判断

服务端 journald 里**没有逐任务时延**（只有失败事件：`desktop_task_failed`、`desktop_tasks_limited`，14 天内都是 0 次），
真正的回合耗时只能从 DSH 会话日志拿到。所以 P0 埋点缺的那一段其实是**客户端侧的等**（事件发生 → 请求发出），
而「回合内耗时」这部分会话日志已经能回答。

## 九、预取资料：海克斯已经在做了，装备还缺一张表

### 海克斯：机制现成，需要的是验证 + 改一句提示词

- 数据：`agent_dsh/data/lol-augment-effects.json`（237 条，覆盖 99%，实测「将他们放倒倒倒」「回归基本功」都能命中）。

- 上下文里客户端只发名字（`client_context.owned_augments`），服务端查表 —— 这个分工是对的：
  名字几十字节，效果文本几百字，塞客户端只会撑爆 2000 字符的 message 预算（此前 413 丢过 20 次建议）。

   它会诱导模型再查一次，应改为「事实包已给出效果文本，直接采用，不要重复检索」。
