# 自动播报延迟优化计划

## 一、先纠正一个判断（实测）

此前我把"播报晚到几分钟"归因于模型慢。实测 `agent-activity.jsonl` 里近 40 个回合：

```
中位数 4.5 秒   均值 5.7 秒   P90 7.6 秒   最大 36.6 秒
<10 秒 36 个 | 10-30 秒 3 个 | 30-60 秒 1 个
```

**模型不是瓶颈。** 真正的延迟在"事件发生"到"请求发出"之间，以及请求被丢弃后等下一次触发。

## 二、目标（可验收）

| 指标 | 现状 | 目标 |
|---|---|---|
| 关键事件（敌方成装 / 海克斯确认）到播报可见 | 3~11 分钟 | P90 ≤ 8 秒 |
| 关键时刻请求被丢弃率 | 未知（无埋点） | ≤ 5% |
| 模型回合 P90 | 7.6 秒 | 保持 ≤ 10 秒 |

## 三、分阶段

### P0 全链路埋点（半天，必须先做）

现在无法回答"这 3 分钟花在哪"。在 auto-coach 里记录带时间戳的阶段事件到 `logs/coach-timeline.jsonl`：

- `event_seen`（事件入队）→ `plan_built` → `scheduler_submit` → `scheduler_take`（含 lane）→
  `ask_start` → `ask_end` → `publish` ；被丢弃时记录 `skip` + 原因（throttle / busy / coalesce / deadline）

验收：任取一条播报，能从日志读出它每一段的耗时。

### P1 去掉对关键时刻的全局节流（1 天）

`auto-coach` 有 `now()-(store.lastAt??-Infinity)<30000` 的全局 30 秒节流。
敌方成装、海克斯确认、团灭这类事件即使命中也要等满 30 秒。

改法：节流只对 `situation`/`opening` 这类"可等待"的事件生效；`postAugment / enemyChange / ace / death` 直接放行。

### P2 请求被占用时的抢占（2~3 天，风险最高）

单一在途请求是 3~11 分钟的主因之一：一个慢回合没结束，后续关键时刻只能被丢弃或排队。

改法：
1. 给请求分级（手动提问 > 关键事件 > 常规刷新）
2. 高优先级到达时取消在途的低优先级回合
3. **必须验证取消的清理**：服务端任务是否真的停下（历史上有僵尸任务占额度的先例）

验收：连续触发两次关键事件，第二次的 `ask_start` 与第一次 `ask_end` 的时间差 < 2 秒。

### P3 事件合并与去重（1 天）

同一波连续事件（三件装备同时成型、连杀）会产生多次请求。按"同类事件 5 秒窗口合并"处理，
合并后只发一次，但播报覆盖全部要点。

### P4 前端呈现兜底（已部分完成）

本地规则先出短句（已做：敌方关键成装、海克斯承接语已按你的要求撤掉承接语），
模型播报到达后覆盖。这条不追求速度，只保证"没有空白期"。

## 四、执行顺序与验证

1. P0 埋点 → 用真实对局数据确认时间都花在哪一段（1 天后给出实测结论）
2. 依据实测结果决定先做 P1 还是 P2（我预期是 P1 便宜且立刻见效）
3. 每阶段都跑一遍上述三项指标，不达标不算完成

## 五、不做什么

- 不为了快而减少事实校验（编造冷却、价格比慢更糟）
- 不用固定模板冒充模型分析（模板只做"第一反应"，不承担分析）
- 不在未验证取消清理的情况下上抢占（僵尸任务会持续消耗额度）
