# 自动播报延迟优化计划

## 一、先纠正一个判断（实测）

此前我把"播报晚到几分钟"归因于模型慢。实测 `agent-activity.jsonl` 里近 40 个回合：

```
中位数 4.5 秒   均值 5.7 秒   P90 7.6 秒   最大 36.6 秒
<10 秒 36 个 | 10-30 秒 3 个 | 30-60 秒 1 个
```

**模型不是瓶颈。** 真正的延迟在"事件发生"到"请求发出"之间，以及请求被丢弃后等下一次触发。

## 二、目标（可验收）

| 指标 | 现状 | 目标 |
|---|---|---|
| 关键事件（敌方成装 / 海克斯确认）到播报可见 | 3~11 分钟 | P90 ≤ 8 秒 |
| 关键时刻请求被丢弃率 | 未知（无埋点） | ≤ 5% |
| 模型回合 P90 | 7.6 秒 | 保持 ≤ 10 秒 |

## 三、分阶段

### P0 全链路埋点（半天，必须先做）

现在无法回答"这 3 分钟花在哪"。在 auto-coach 里记录带时间戳的阶段事件到 `logs/coach-timeline.jsonl`：

- `event_seen`（事件入队）→ `plan_built` → `scheduler_submit` → `scheduler_take`（含 lane）→
  `ask_start` → `ask_end` → `publish` ；被丢弃时记录 `skip` + 原因（throttle / busy / coalesce / deadline）

验收：任取一条播报，能从日志读出它每一段的耗时。

### P1 去掉对关键时刻的全局节流（1 天）

`auto-coach` 有 `now()-(store.lastAt??-Infinity)<30000` 的全局 30 秒节流。
敌方成装、海克斯确认、团灭这类事件即使命中也要等满 30 秒。

改法：节流只对 `situation`/`opening` 这类"可等待"的事件生效；`postAugment / enemyChange / ace / death` 直接放行。

### P2 请求被占用时的抢占（2~3 天，风险最高）

单一在途请求是 3~11 分钟的主因之一：一个慢回合没结束，后续关键时刻只能被丢弃或排队。

改法：
1. 给请求分级（手动提问 > 关键事件 > 常规刷新）
2. 高优先级到达时取消在途的低优先级回合
3. **必须验证取消的清理**：服务端任务是否真的停下（历史上有僵尸任务占额度的先例）

验收：连续触发两次关键事件，第二次的 `ask_start` 与第一次 `ask_end` 的时间差 < 2 秒。

### P3 事件合并与去重（1 天）

同一波连续事件（三件装备同时成型、连杀）会产生多次请求。按"同类事件 5 秒窗口合并"处理，
合并后只发一次，但播报覆盖全部要点。

### P4 前端呈现兜底（已部分完成）

本地规则先出短句（已做：敌方关键成装、海克斯承接语已按你的要求撤掉承接语），
模型播报到达后覆盖。这条不追求速度，只保证"没有空白期"。

## 四、执行顺序与验证

1. P0 埋点 → 用真实对局数据确认时间都花在哪一段（1 天后给出实测结论）
2. 依据实测结果决定先做 P1 还是 P2（我预期是 P1 便宜且立刻见效）
3. 每阶段都跑一遍上述三项指标，不达标不算完成

## 五、不做什么

- 不为了快而减少事实校验（编造冷却、价格比慢更糟）
- 不用固定模板冒充模型分析（模板只做"第一反应"，不承担分析）
- 不在未验证取消清理的情况下上抢占（僵尸任务会持续消耗额度）

### P0 为什么不达标

三个缺口：

1. **没有 turn id**。按「同局同 stage」硬配对，30 条播报算出中位 **515 秒**——纯属假数据；
   改成单飞配对（running→首个收尾事件）才对上 **22.2 秒**。现在谁读这份日志都会读错。
2. **没有 `event_seen / plan_built / scheduler_submit / scheduler_take / ask_start / ask_end`**。
   能读出「模型回合总耗时」，读不出「事件发生 → 请求发出」那段，而计划第三节明确说延迟就在那段。
3. **没有报告脚本**，只能人工写一次性分析。

### P1 复核时查出的两个新缺口

原计划以为「把 30 秒节流只留给可等待事件」就完事。实际复核发现节流搬了家：

1. `automatic-pacing.mjs` 的准入层有 `intervalMs = 60000`（按 topic 计）。`main.mjs` 没传值，走默认 60 秒。
   而 `allowed = !active && (urgent || !busy())` —— **urgent 只豁免语音队列 busy，不豁免这个 60 秒间隔**
   （`openFor()` 对 urgent 一视同仁）。后果：一次团灭/死亡边沿若落在上一次播报后 60 秒内，
   会被 `auto_deferred` 推到下一次，而死亡窗口只有 45 秒。
2. `auto-coach` 的抢先判断用的是 `canRequest()`，它只反映 `allowed()`，**不反映 `openFor()`**。
   于是「死亡不受背压限制」这条前置放行在真正的准入点被否掉，调度器再聪明也来不及。
   这就是 `retry_backoff` 116 次与 `output_backpressure` 568 次里的一部分。

这类豁免没有测试保护（`automatic-pacing-urgent.test.mjs` 只测了 busy 与单飞），所以一直没被发现。

### P2 路线复核（2026-11-15）：后台并行走不通，抢占其实可测

原本设想「急事另起一个后台任务并行跑，谁先回来先用」。查了服务端实现，这条路被策略挡死：

- `tasks.py create()` 里 `if any(task["owner"] == owner for task in active): raise TaskError("user_task_busy", 409)`
  —— **一个账号同时只允许一个未终态任务**。所以客户端的单飞不是偷懒，是服务端规定。
- 全局 `ThreadPoolExecutor(max_workers=max_running)`，`max_running = 2`
  —— 整个服务同时只跑 2 个任务，第 3 个直接 429 `agent_capacity`。同一玩家并行 2 个会挤掉别人。
- 就算放开，同一 `(owner, session)` 并发也不安全：`create()` 快照 `history`，任务结束时 append 用户和助手消息，
  两个并发任务会各 append 一遍，历史重复错序。

但「取消」这条路是真的能做，而且已经写好了，只是没人用：

- 服务端 `cancel()` 只设置 `threading.Event`，`runner` 在每一步之间检查，命中就 `process.kill()`
  杀掉子进程并抛 `task_cancelled`；`_run` 收尾时再判一次，状态落成 `cancelled`。
- 客户端 `createCloudAgent.close({reason:'preempt'})` 已经会打 `/tasks/:id/cancel`，并轮询到终态（上限 45 秒）。
- 手动提问抢占自动回合走的就是这条链，已有测试覆盖（`priority-recovery.test.mjs`）。

**结论：P2 不需要新机制，需要把「手动提问抢占」这套接给关键自动事件**（死亡边沿、海克斯确认、团灭）。
风险从「未知」降为「可测」：取消后服务端子进程被 kill，可以再实测一次
「取消后 activity 里不再出现 model_start/model_end、额度不再增长」来收口。

### 埋点顺手暴露的真主因（优先级应重排）

`skip` 原因分布（2 小时 17 分）：

| 原因 | 次数 | 含义 |
|---|---|---|
| `stale_facts` | 934 | 对局日志静默超过 2 分钟，整局被判死 |
| `output_backpressure` | 568 | 语音队列背压，事件被吞 |
| `busy` | 424 | 单飞：上一个回合 15~37 秒没跑完 |
| `no_live_match` | 166 | 无对局/已结束 |
| `retry_backoff` | 116 | 失败退避 |

结论：**播报丢的第一主因不是节流，是对局日志断流（934 次）**；第二是语音背压（568）；
第三才是排队（424，P2 想解决的正是这一段）。这跟第四节“依据实测决定先做 P1 还是 P2”的约定一致——
现在该先修断流与背压，抢占排在第三。
